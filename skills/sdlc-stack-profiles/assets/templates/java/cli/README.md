## The CLI contract

Scripts and agents consume this tool, so its interface is an API:

- **Streams.** Primary data goes to **stdout**; diagnostics,
  progress, and errors go to **stderr**. Nothing but data is ever
  written to stdout.
- **Exit codes.** `0` success · `1` failure (the command ran but
  could not complete) · `2` usage error (unknown command, bad
  flags, invalid arguments). The map is also printed by `--help`.
  (picocli's defaults already are this map; failures raised after
  parsing are mapped by an execution exception handler.)
- **Formats.** `--format plain|json` (or `--json`) on data
  commands. In JSON mode the output is an object with a stable
  `result` field. `--version` prints `{{project-name}} X.Y.Z` —
  the version comes from the pom via a filtered
  `version.properties`, so the jar, the tests, and the app image
  all report the same value.
- **Colour.** Diagnostics are styled only at a terminal, and never
  when `NO_COLOR` is set or `--no-color` is passed.
- **Safety.** Results written with `--out` are never overwritten
  without `--force`; `--dry-run` reports what would happen and
  writes nothing; prompting happens only at a terminal, and
  `--no-input` disables it entirely (the command fails instead).
- **Configuration precedence.** Flags, then environment
  (`<PREFIX>_FORMAT` and friends — the prefix is the tool name
  upper-cased with hyphens as underscores, e.g.
  `TASK_TRACKER_FORMAT`), then defaults. Secrets come from the
  environment, never from a flag (flags leak into shell history
  and process lists). Environment precedence is verified against
  the packaged jar in CI (a JVM cannot set its own environment
  portably).

The contract is pinned by tests: golden files for help and primary
outputs, and exit-code tests per failure mode
(`src/test/java/.../cli/CliContractTest.java`). Regenerate goldens
deliberately with `./mvnw test -Dupdate.golden=true` and review
the diff like an API change — changes to the JSON schema, the exit
codes, or flag names are **breaking changes** and ship only in a
major release. One surface differs by ecosystem: picocli generates
bash/zsh completion scripts (`zsh` via bashcompinit); it has no
fish generator, so `completions fish` is a usage error here.

## Versioning and releases

Strict semantic versioning. The version lives in `pom.xml`;
releasing means moving the CHANGELOG *Unreleased* entries under a
`## [X.Y.Z] - YYYY-MM-DD` heading, bumping the pom to match, and
tagging `vX.Y.Z`. The release workflow refuses a mismatched tag or
a missing CHANGELOG section, tests, then builds jpackage app
images per platform, generates a man page (help2man) and shell
completions from the shaded jar, publishes a GitHub Release with a
SHA-256 `checksums.txt`, and deploys the artifact to Maven
Central.
